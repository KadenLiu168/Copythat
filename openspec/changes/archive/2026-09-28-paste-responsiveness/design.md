## Context

See `proposal.md` for motivation and `specs/paste-and-permissions/spec.md` for the behavior contract. `ClipboardPastePerformer.paste()` currently writes via `ClipboardStore`, checks target and Accessibility through `pasteDecision`, calls `NSRunningApplication.activate`, then schedules `sendCommandV()` after 350 ms. `PanelWindowController` closes the panel immediately when `paste()` returns `true`. `CopySourceTracker` has its own long-lived activation observer for attribution; it is not a paste coordinator.

## Goals / Non-Goals

**Goals:** Keep the current synchronous `paste()` return/close contract and safety gates; coordinate target activation and 350 ms fallback with deterministic at-most-once cancellation; keep system-event details local to the paste service.

**Non-Goals:** Rework target selection, source attribution, synthetic key delivery, or the existing pasteboard/permission handling. No new timing threshold or general-purpose activation framework. The existing 350 ms deadline still initiates fallback; fallback delivery shares the asynchronous main-queue send and may run one queue dispatch after the timer fires, rather than claiming exact wall-clock event delivery.

## Decisions

1. **One main-actor attempt owned by `ClipboardPastePerformer`.** Give each attempt a unique token and target PID, and track its observer, cancellable fallback, and queued send. At the start of every new `paste()` request, invalidate any older attempt (including a queued-but-not-yet-sent command); this prevents an old paste from acting on newly written clipboard content even if the new request fails prerequisites. Keep `pasteDecision` and the existing return semantics: `true` means restore and prerequisites passed and coordination began, not that the key was already sent. Alternative: put coordination in `PanelWindowController` or `CopySourceTracker`; both would mix responsibilities.

2. **Observe before activating; confirm the exact target.** Once restore and prerequisites pass, install a short-lived `NSWorkspace.didActivateApplicationNotification` observer *before* calling `activate(options: [.activateAllWindows])`. Only notifications whose application's `processIdentifier` matches the captured target PID qualify. Check `isActive` or the frontmost PID immediately before and after `activate()` so an already-active target and synchronous activation do not wait for a missing edge notification. Keep activation request even on the already-active path to preserve current behavior. Alternative: polling or waiting only on notifications introduces needless complexity or misses already-active targets.

3. **Single terminal claim, deferred delivery.** Activation confirmation schedules delivery asynchronously on the main queue after the current synchronous paste call returns; the 350 ms timer is scheduled from the activation request as a compatibility fallback, not a required wait on the normal path. Both routes pass through one token-checked completion; it atomically claims this attempt on the main actor, removes the observer and cancels the fallback before queuing the key event. The queued send rechecks that its token has not been invalidated by a newer `paste()` call or deinit. Ignore later callbacks, including callbacks already enqueued when the observer was removed. Timer fallback does not require active-state confirmation, matching current behavior. Use `DispatchQueue.main.async` for deferred delivery, so the synchronous caller can close the panel first; do not use `Task.yield()` or promise a numbered CFRunLoop iteration. Establish the attempt token and install the observer and cancellable fallback before calling `activate()`, with the fallback deadline anchored immediately before that activation request. A matching notification may arrive synchronously inside `activate()`; completion must then find both cleanup handles installed, and the post-activation check must not rearm a completed attempt. The pre-activation active-state check records readiness, but delivery is claimed only after the activation request has been made (or by its callback). Observer and timer callbacks execute on the main actor; callback hops, if required, recheck the token when processed. Alternative: independently dispatching from observer and timeout can paste twice; replacing 350 ms with a shorter constant trades reliability for speed.

4. **Test only the system boundaries needed for coordination.** Introduce small injected closures/objects with production defaults for observing activation, checking active state, requesting activation, scheduling/cancelling fallback, deferring a main-queue turn, and recording/sending Command-V, so tests can control callback order without launching other apps, sleeping, modifying the real pasteboard or posting CGEvents. Keep the real `paste()` restore/permission gates intact; an internal coordinator entry point can exercise successful coordination independently. Cancellation on request entry must also be tested through the actual `paste()` method: reuse a uniquely named `NSPasteboard`, `ClipboardStore(initialItems: [], persistItems: { _ in })`, isolated settings and `CopySourceTracker()` without calling `start()`. Start an older pending or queued attempt, then submit an un-restorable item or a restorable item with no target through `paste()`; assert the existing `false` return and exact failure message, and drain stale callbacks to prove no send. These paths short-circuit before the Accessibility prompt and need no permission seam. Existing `PasteDecisionTests` continue to cover failure precedence. Release the named pasteboard and isolated settings after each test; never load or save real clipboard history. No broad protocol hierarchy. Production closures use the AppKit APIs and existing CGEvent implementation.

## Risks / Trade-offs

- [Activation event precedes observer registration or target is already active] → Register before `activate()` and check active state on both sides of activation.
- [Timer and notification both fire, or callback already queued] → Main-actor token claim plus cleanup; verify both callback orderings and late callback.
- [A second paste arrives before the first deferred key event] → Invalidate old token at request entry and check token again when the queued send runs.
- [Target loses focus between activation confirmation and key delivery] → The fast path uses only one main-queue turn, not a fixed sleep; validate focus/paste manually with a real target and inspect any observed regression rather than changing target/fallback semantics in this change.
- [Observer or task retains the performer indefinitely] → Explicit cleanup on completion, supersession and deinit; use weak captures and cancellable scheduling. A performer that is deallocated must never later post Command-V.
- [Activation notification absent in unusual apps or Spaces] → Keep the existing unconditional 350 ms fallback; real-world activation latency is not promised to be below a numeric threshold.

## Migration Plan

No data or API migration. Ship behind existing paste flow after deterministic coordination tests, `swift build`, `./script/verify_all.sh`, and a manual paste/focus/duplicate smoke test through the actual Copythat panel into a controlled target app. The existing `runRestorePaste` driver bypasses the performer by calling `store.writeToPasteboard` and its own `keystroke("v")`; use it only if extended to invoke the real performer. Record target app, Accessibility state, tested cases, observed content and duplicate count, panel dismissal/focus outcome, and environment limitations. A permission-blocked smoke test is pending evidence, not a pass. Rollback is limited to restoring the prior fixed-delay coordination; permission and restore contracts remain unchanged.

## Stage 1 findings and disposition

- **Pre-implementation fix — installation ordering:** The initial design did not order fallback installation against a synchronous activation notification, allowing cleanup to run before a handle existed. Decision 3 now requires both handles before activation and forbids rearming after a terminal claim. Tests must cover a notification inside `activate()` and already-active checks without notifications.
- **Pre-implementation fix — request-entry acceptance:** Existing `PasteDecisionTests` prove only pure decision precedence; a coordinator-only test cannot prove invalidation happens before restore and early returns in `paste()`. Decision 4 and task 1.3 now require real-entry failure tests with isolated store/pasteboard fixtures.
- **Pre-implementation fix — integration evidence:** `script/verify/clipboard_live_driver.swift:runRestorePaste` bypasses this service. Proposal, migration plan and task 3.2 now require the real panel/performer path and explicit observations; an unchanged driver or blocked run cannot satisfy acceptance.
- **Pre-implementation fix — deferral terminology:** Define the existing intended deferred send as asynchronous main-queue delivery after the synchronous caller returns, rather than a numbered run-loop iteration. No numeric normal-path latency guarantee is added.
- **Recorded tradeoff — foreground/permission changes:** The unconditional fallback and existing entry-time Accessibility check remain unchanged. The event goes to the then-foreground application; no new delivery-time target/permission gate is introduced. A focus change after confirmation remains a compatibility risk to inspect in the real-app check, not a guarantee that this change solves.
